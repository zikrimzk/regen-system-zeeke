# Phase 00 · Data mapping and migration plan

This is a source-schema inventory. `database/schema.sql` declares 64 InnoDB tables with `utf8mb4`, uses MySQL/PDO, and contains fresh-install seeds and later `ALTER TABLE` statements. Upgrade scripts are the numbered SQL files 002–027. The current installation's engine/version, applied scripts, schema drift, row counts and DDL duration are unknown. Phase 00 inspects SQL and repository queries only.

Compare actual columns, indexes, foreign keys, grants and data effects to both schema paths. Fresh schema and upgrades can differ even when table names agree. Fresh SQL includes `mochi_coach` in the strict pricing seed while incremental 024 does not, and 027 adds the preference table only. Compare effective policy as well as the presence of stored prices. `Application::health()` samples selected tables and columns while omitting `payment_orders` and some grant/reservation tables; a green response is insufficient to certify 027 or payment readiness. No persistent migration-tracking mechanism was identified in the executable source. Record applied IDs, checksums and actual postconditions in Phase 01 and add forward migrations with a reliable ledger before new V2 schema work.

## Backup, rollout and recovery gates

1. **Establish baseline.** Obtain authorized schema metadata and counts, no raw personal rows in engineering output. Record engine/version, time zone, collation, storage path/writable state, migration postconditions, deployed artifact hash and source contents. Confirm release staging is based on a reviewed working tree, since `release.json` cites HEAD even when packaging local uncommitted files. Rehearse with synthetic fixtures or a purpose-approved sanitized copy and stub all external providers.
2. **Back up consistently.** Agree who can access backup material and acceptable recovery point/time. Capture a transactionally consistent MySQL/MariaDB backup, current artifacts and private storage including attachments, any portal SMTP override and its key, retained legacy uploads and licensed fonts. Coordinate snapshot timing or quiesce relevant writers for file/DB consistency. Store production configuration and credential-bearing storage through the existing restricted secret process. Validate backup integrity by a restore into a separate environment and compare aggregate counts, checksums, ownership and file references. Resume snapshots are application-level recovery, separate from disaster recovery.
3. **Expand compatibly.** Attach versioned, additive migrations and schema assertions with per-environment metadata. Prefer nullable columns, small referenced tables, indexed owner queries and unambiguous defaults. Test non-transactional DDL interruption, lock duration and fresh/upgrade parity. Keep existing code able to run against the expanded schema. Apply a verified migration at staging only after backup, reviewed steps and approval for any destructive or billable operation.
4. **Backfill carefully.** Use ordered bounded batches, checkpoints and an idempotent source key. Log aggregate counts and mismatch classes, with no document text. Check orphan/duplicate rows, owners and dates, normalized JSON shape, template distributions, attachment references, wallet-ledger balance, held credits, grant/receipt links and `payment_orders` totals by state/mode/currency. Quarantine exceptional mappings for review, especially if candidate confirmation is needed. Re-run the batch safely and test concurrent owner edits or worker activity.
5. **Switch by route/feature.** Move reads and writes in small cohorts after comparing legacy/new results under the same policy. Only dual-write when the same transaction or idempotent handoff can guarantee convergence. Preserve existing grants, IDs, callback ingress and signed event processing. Check error rate, pending checkout backlog, PDF parity, unexpected access changes and outbox lag before widening exposure.
6. **Roll back code or traffic first.** Disable new features and restore known-good routing and artifact while retaining additive data. Keep the payment callback contract processing through a known-good handler. Reconcile post-cutover writes and new payment confirmations before any DB restoration; restoring an old snapshot blindly could lose paid benefits or new drafts. Reverse a data transform only from its documented idempotent journal and verified backups after approval. Unlinking old routes or dropping columns is a later, separate reviewed change after retention, restore and migration gates pass.
